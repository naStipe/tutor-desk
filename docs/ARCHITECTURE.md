# TutorDesk Architecture

## Architectural Philosophy

TutorDesk is designed as a **TypeScript Modular Monolith**. It prioritizes clarity, velocity, maintainability, and operational simplicity for a small engineering team.

We explicitly reject distributed systems complexity (microservices, distributed event buses, separate frontend/backend repositories) in favor of a cohesive, single-repository full-stack structure.

---

## Core Stack

* **Framework**: Next.js App Router (React, Server Components, Route Handlers, Server Actions).
* **Language & Runtime**: Strict TypeScript on Node.js (v22+).
* **Database**: PostgreSQL, with an official PostgreSQL 17 Docker image and persistent volume for local development.
* **ORM & Query Builder**: Drizzle ORM (`drizzle-orm` and `drizzle-kit`).
* **Authentication**: Better Auth infrastructure with PostgreSQL session and user storage. Authentication UX and tutor authorization are not yet implemented.
* **Validation**: Zod schemas for all runtime inputs, environment variables, and API payloads.
* **Styling**: Tailwind CSS for responsive, accessible utility-first styling.
* **Formatting and Static Analysis**: Biome, with TypeScript type checking as a separate check.
* **Testing**: Vitest for unit/integration tests and Playwright for end-to-end browser verification.
* **Continuous Integration**: GitHub Actions executing format, lint, typecheck, test, and build pipelines.

## High-Level Repository Structure

```
tutordesk/
├── src/
│   ├── app/                 # Next.js App Router (pages, layouts, route handlers)
│   ├── components/          # Shared, reusable UI components (buttons, dialogs, inputs)
│   ├── features/            # Feature-oriented domain modules (auth, students, lessons, etc.)
│   ├── db/                  # Database connectivity, schemas, migrations
│   │   ├── schema/          # Drizzle schema definitions
│   │   ├── migrations/      # Versioned SQL migration files generated by Drizzle Kit
│   │   └── index.ts         # Initialized DB client and connection pool
│   ├── lib/                 # Shared utilities, environment validation, auth helpers
│   └── test/                # Test utilities, mocks, unit/integration test suites
├── docs/                    # Architecture, product, and domain documentation
├── AGENTS.md                # Agent operating rules
├── README.md                # Project setup and developer instructions
├── .env.example             # Documented environment variables with safe defaults
├── package.json             # Dependencies and scripts
└── pnpm-lock.yaml           # Locked dependency graph
```

## Key Architecture Principles

### 1. Unified Modular Monolith
* Frontend and backend reside in a single codebase and deploy as a single unit.
* There is no separate API microservice or detached backend repository. Next.js Server Components and Route Handlers provide the backend boundary.

### 2. Feature-Oriented Organization
* Code is organized by domain feature inside `src/features/` (e.g., `students/`, `lessons/`, `invoicing/`).
* Each feature encapsulates its own validation schemas, domain logic, and feature-specific components.
* Shared infrastructural concerns live in `src/components/`, `src/lib/`, and `src/db/`.

### 3. Server-Side Authorization Invariant
* Authorization is never trusted to the client.
* Every database query and business operation must verify the active user session and enforce that all accessed resources belong strictly to the authenticated tutor (`tutorId` scoping).
* Cross-tenant access must return a 404 or 403 error.
* This is a design invariant for future tutor-owned resources, not functionality delivered by TD-000.

### 4. Direct, Type-Safe Data Access
* Drizzle ORM provides typed queries mapped directly to PostgreSQL tables.
* We avoid the generic repository pattern, verbose service-layer abstractions, or object-relational abstraction layers that add ceremony without value.

### 5. Deliberate, On-Demand Integrations
* External integrations (e.g., email delivery, Google Calendar, payment processors) will be introduced strictly when explicit product requirements demand them, adhering to clean boundary abstractions.
